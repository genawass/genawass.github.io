Shared Storage Is Not Redundancy

August 13, 2026

Putting the database on the cluster's shared mount feels like the careful choice. Every node can see it, and if a machine dies the file is still there. The second half is true and the first half is a trap — and the measurement that shows why also decides where the code should live.

The system in question is small and unglamorous: a Jira-shaped issue database for one person, driven by AI agents working across a compute cluster. Agents file issues, attach watches to training jobs, record metrics against targets, and a digest lands before the morning review. SQLite, Python standard library, no dependencies. The whole thing is under two megabytes of data.

It was laid out the obvious way. The database sat on the NFS mount at /mnt/datasets/tam/data/tam.db, and the code sat next to it at /mnt/datasets/tam/code so that every node could run tam without an install. One place for everything, visible everywhere. That arrangement survived exactly as long as nobody asked what it was actually providing.

The framing that helps: a shared filesystem gives you visibility from many hosts. It does not give you concurrent access, and for a single-file database those are not the same purchase. Once you measure that only one host can open the file safely, three things follow. The mount is not buying availability. The second copy of the code is not buying convenience, it is buying drift. And the redundancy you thought you had needs to be bought separately, somewhere else.

The mount does not disappear. It stops being authoritative and starts holding only things that are written once and never contended.

What two hosts actually do to a SQLite file

This is worth measuring rather than reasoning about, because the failure is not the one people expect. The expectation is corruption — a mangled file, an integrity check that screams. What actually happens is quieter and worse.

Two hosts writing the same file on an NFSv4 mount, three hundred writes each:

journal moderesult
WAL (the default, and the fast one) The second host lost 100% of its writes. disk I/O error, loudly, on every attempt.
TRUNCATE (rollback journal) Both hosts wrote successfully. 11% of writes vanished — 33 of 300 — with no error anywhere.

The WAL result is the good one. WAL keeps coordination state in a shared-memory index file that has no meaning across machines, so the second host fails immediately and obviously. You find out in seconds.

The rollback-journal result is the dangerous one, and it is what you get if you "fix" the WAL error by changing journal modes. NFS advisory locking is not strong enough to serialise the writers, so both of them believe they succeeded and one in nine updates is simply gone. There is no error to alert on and no log line to grep. You discover it weeks later when someone asks why a task they closed is open again.

The diagnostic that matters: if a shared-storage database appears to work with two writers, that is not evidence it is safe. It is evidence you are in the mode that loses writes silently.

The corollary nobody draws

The usual response to this measurement is a guard, and we wrote one: the config records which host owns the file, every other host is refused with a clear error and a non-zero exit code, and an environment variable lifts the guard for deliberate takeover. That is correct and it stopped the bleeding.

It also left the interesting question unasked for months. If exactly one host may ever open the file, what is the shared filesystem contributing?

Not availability — a second host could never serve from that file, by measurement. Not durability in any meaningful sense — NFS redundancy protects against a disk failing, not against a bad migration, a wrong DELETE, or the file being removed. What it contributed was a corruption surface and a standing invitation to try the thing that loses writes.

The code copy had the same shape of problem. Staging the tree on the mount meant every node could run the CLI without an install, which is genuinely convenient right up until the copy on the mount and the checkout on the serving host disagree. Ours did. The fix at the time was a publish script — refuse to publish a dirty tree, rsync with --delete, stamp the deployed commit into a dotfile — and it worked. But a script whose entire job is keeping two copies identical is a strong hint that the second copy should not exist.

The question that resolved it: what does a node actually need in order to be useful?

Not the code. The answer was an address and a token. Everything else — the CLI, the agent tooling, the board — was a client of an HTTP API that already existed and already enforced every rule server-side. The shared code tree was solving a problem the API had already solved.

What replaced it

The database moved to local disk on the one host that was already the only permitted writer. Nothing about the write path changed, because nothing about the write path could ever have been shared. What changed is that the constraint is now enforced by physics instead of by a guard and a README: there is no second path to the file.

Every other node became an HTTP client. That was mostly a deletion: the remote CLI presents the same method surface as the local service, so the command-line tool runs against a remote database with no branching, and a parity test diffs the two public surfaces so a method added to one and not the other fails the build. The agent-facing documentation moved into the repository and is now served by the same API that enforces the rules it describes — a node reads its instructions from the host that will accept or reject its writes, so the two cannot drift.

The shared mount kept exactly three things, and the list is the point:

  • An environment file with two variables — the API URL and the token. It is the bootstrap, and it is deliberately not code.
  • The token itself, so rotation is one file that every node picks up on next login.
  • Snapshots. The database now lives on a single local disk, so backups must land somewhere else or they are not backups. This is the one job the mount was always good at: holding things that are written once and never contended.

That last point is the trade made explicit. The old arrangement felt redundant and had no off-host copy of anything. The new one is openly single-host and has a consistent, integrity-checked snapshot on separate storage. The second is strictly safer, and it only looks worse.

What "not a single host" actually costs

Making this genuinely multi-host is a real question with an unpopular answer, and it is worth separating the two failure modes before spending anything.

Durability — the disk dies and the data is gone. This is cheap. Snapshot to other storage on a timer. A two-megabyte database can be snapshotted every couple of hours for effectively nothing, and SQLite's online backup API produces a consistent copy even against live writers, which a filesystem-level copy of a WAL database does not.

Availability — the host is down and nobody can file anything. This is where the money goes, and the honest options are tiered:

  • Warm standby. Frequent snapshots plus a promote script that restores, starts the service, and repoints the address. Recovery in minutes, no new software, every guard and index intact. The address lives in one file on shared storage, which makes promotion a one-line edit rather than a change on every node.
  • Continuous replication. Stream the WAL to another host and the recovery point drops from hours to seconds. One binary, no schema change.
  • An actually distributed database. Automatic failover, multiple writers, and a rewrite: a different storage engine, full-text search replaced, every guard retested, and a cluster to operate forever. For a single-user system this is spending weeks and permanent operational cost to avoid a manual step that fires once a year.

Most systems that reach for the third option needed the first one. The instinct to avoid a single point of failure is right; the reflex to solve it with a distributed datastore usually is not, and a shared filesystem is that reflex in its cheapest and most misleading form.

The bill for making everything a client

Every architectural choice sends an invoice, and this one arrived during the migration itself.

Once every node is an API client, every working shell holds production credentials — that is what the environment file is for. The test suite reads the same variables, and the CLI treats a set API URL as "use the remote service". So a single command that sourced the environment file and then ran the tests pointed the entire suite at the live database. Twenty-five test fixtures — issues titled b0, late, Parity — were created in production, and the suite reported them as failures rather than as what they were.

The fix is four lines: the test fixture now clears the client variables, so a suite can never inherit a pointer at the real service. The lesson is not four lines. Under the old layout this failure was impossible, because reaching the data required being the owner host. Making every node a client is the right architecture and it widens the blast radius of an ambient environment variable to include everything. If your credentials are in every shell by design, your test harness must assume they are there and refuse them explicitly.

What to take from this

The generalisable part is not about SQLite or NFS. It is that infrastructure gets adopted for the property it appears to have rather than the one it delivers, and a shared filesystem is unusually good at appearing. It looks like redundancy, it looks like distribution, and it looks like a deployment mechanism, while actually providing visibility and nothing else.

The test that separates the two is cheap: name the failure the component is supposed to survive, then check whether it actually survives it. If the answer is that only one host can use the thing anyway, you are not running a distributed system. You are running a single-host system with extra steps, and the honest version of it is both simpler and safer.
